# Harness Enforces Memory

> 以下是帖主和 Claude Code 对话中的思考记录。不是权威指南，是思维痕迹本身。

## 0. 这个记忆系统在干嘛

跨 session 持久化信息。一个 session 结束后上下文就丢了，下次启动模型不记得上次聊了什么。记忆系统把值得跨 session 的信息存到磁盘，下次加载回来。

```
session 1: "我喜欢 tabs" → save_memory → 写 .md 文件
session 2: load_all() 读回来 → 拼进 system prompt → 模型看到
```

## 1. 四种方案（帖主和 Claude Code 探讨的产物）

核心矛盾：记忆有用，但全塞进 system prompt 太贵了。

当前代码把所有记忆全文塞进 prompt。省事，但浪费。四个方向是聊出来的解法，不是标准答案：

**方案一：Index in prompt, content via tool**
System prompt 只放一行摘要，想看全文调工具读文件。代码已经写了索引和工具，只差 `load_memory_prompt` 不输出全文。改动最小，收益最大。

**方案二：Hot / Cold 分层**
最近访问过的升温进 prompt，长期不用的降级成纯索引。LRU cache。

**方案三：向量检索**
入库算 embedding，启动时语义搜索召回 top-K。精准但多一套基础设施。

**方案四：LLM 压缩**
定期把一堆记忆压缩成一段摘要。难点是 lossy 压缩的累积误差。

四个方案可以叠加。你只有一个变量要决定：**把有限的 context window 预算分配到哪里。**

## 2. 记忆的本质是"决策辅助层"

这是对话里最核心的洞察。

记忆系统的目的不是"存数据"。存数据不是问题，磁盘很便宜。

真正的问题是：一个 session 启动时，你给模型看什么、不看什么。这个选择直接决定模型的行为质量。所以记忆系统的本质是一个**决策辅助层（signaling layer）**——你在帮模型判断"什么东西值得我知道"。全文塞进 prompt 相当于强迫模型每次读整本书，而不是给一本目录让它自己选章节读。

## 3. 四种类型的出处：不是理论，是经验

user / feedback / project / reference 不来自任何论文。来自真实的编码协作场景：

```
"我喜欢 tabs"                  → user（对齐偏好）
"别 mock 数据库，之前出过事故"   → feedback（纠正行为）
"auth 重写是因为合规要求"        → project（代码里看不出的约束）
"bug 看板在这里"                → reference（外部资源指针）
```

价值不在理论完备，在恰好覆盖了模型最常见的四类信息盲区。

## 4. Memory 是乘法，Skill 是加法

Memory 是乘法。每次 session 都在累加，涨到某个点就必须处理"太多了怎么办"——截断、压缩、遗忘。乘法注定需要 GC。

Skill 是加法。稳定的工作流，加一条不会让系统变重，但得让模型知道"有这个可用"。加法不需要 GC。

增长模式不同，加载方式也不同：

```
    Memory                           Skill
  ┌──────────────────┐           ┌──────────────────┐
  │  乘法，动态积累    │           │  加法，稳定集合    │
  │  需要 GC          │           │  不需要 GC         │
  │  加载：PUSH       │           │  加载：PULL        │
  └──────┬───────────┘           └──────┬────────────┘
         │                               │
         ▼                               ▼
  Session 启动                        模型决定需要
      ↓                                  ↓
  系统把记忆推入                       模型主动拉取
  模型 context →                       skill 内容 →
  model receives                      model fetches
```

**Push** —— 模型是被接收方。系统替它决定看到什么记忆。适合少量、高确定性的信息。

**Pull** —— 模型是主动获取方。它自己判断需要什么就去加载什么。适合大量、低频率使用的信息。

Push 和 Pull 不是谁对谁错。是增长模式决定了接入方式。

## 5. Dream 的七道门闸

Dream 是跨 session 的记忆整理工：合并重复、清理过时、截断太长的索引（MEMORY.md）。

整理就是写入，写入就需要保护。七道门闸是"我现在真的应该写入吗"的逐级检查：

```
门 1: enabled 开关没关？
门 2: 有记忆文件可整理？
门 3: 不在 plan mode？（只读模式不写）
门 4: 距上次整理 ≥ 24 小时？（频率控制）
门 5: 距上次扫描 ≥ 10 分钟？（更细的频率控制）
门 6: 至少 5 次 session 的数据？（样本太少不值得）
门 7: PID 锁没人占着？（并发控制）
```

拆开看就是三层通用工程模式：

```
频率限制  →  门 4、5
前置条件  →  门 1、2、3、6
并发控制  →  门 7
```

**PID 锁** — 多个进程可能同时触发整理（两个终端、VS Code + CLI），没锁会互相覆盖。PID 锁是最简单的分布式锁：写自己进程号进锁文件，别的进程看到活着的锁就跳过。

**200 行截断** — MEMORY.md 是索引，也会被加载到 context。没了截断它会无限膨胀。截断不是说记忆丢了 —— 原始 .md 文件还在磁盘上，只是索引不列它了。资源约束下的优雅降级。

## 6. "Harness 本质就是工程"

把记忆系统的概念剥掉 AI 外壳：

```
Dream 的 7 道门闸      → 频率限制 + 前置条件 + 并发控制
200 行截断             → 资源约束下的优雅降级
_rebuild_index         → 缓存索引重建
PID 锁                 → 分布式锁（同一台机器版）
Hot / Cold 分层        → LRU cache
Index + content pull   → 元数据 + 按需加载
Push / Pull 范式       → 所有系统都在做的选择
```

LRU cache 是最典型的例子。一听"AI 记忆系统分层"觉得好高深，剥开看就是缓存系统里最经典的分层策略，数据访问频次驱动升温降温。你把这个系统重构成"最近用过的自动升温进 prompt，长期不用的降级"——你就在写 LRU cache。

区别只在于系统里多了一个 AI 模型作为执行者。但你设计它周围的环境时，调用的依然是操作系统、分布式系统、缓存系统几十年前就沉淀下来的工程模式。

**"Harness 本质就是工程"** 不是说工程简单，是说你别被 AI 两个字吓住。你面对的是工程问题，用工程思维去解决。

## 7. "思考到工程难点"是身份转换的分界线

不是敲键盘那一刻成为工程师的。是你做决定时脑子里浮现的不再是"哪个 API 能实现"，而是**"这个设计的核心权衡是什么"**。

```
用户：      这个怎么用？
工程师：    这个的核心权衡是什么？
设计师：    如果重新设计，我选什么 trade-off？
```
