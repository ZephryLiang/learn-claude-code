# 03 — 架构决策

> 面试里"为什么选这个"比"用了什么"重要 10 倍

---

## 1. 单 Agent vs 多 Agent

**标签**: `arch/single-vs-multi`

### 决策公式

```
多 Agent 不应使用，除非满足全部条件：

1. 单 Agent 准确率 < 45%（DeepMind 基线悖论）
2. 子任务天然可解耦、非严格顺序依赖
3. 你能承受 4.4x-17.2x 的错误放大
4. Agent 数量 ≤ 4（Google DeepMind 黄金分割点）
5. 有 Manager 集中审核（而非独立自治）
```

### 关键数据

| 数据点 | 数值 |
|--------|------|
| 单 Agent 准确率 >45% 时多加 Agent 的收益 | 负 |
| 串行依赖任务多加 Agent 的暴跌 | -39% ~ -70% |
| 工具 >16 种时多 Agent 的协调崩盘 | 高频 |
| 70% 多 Agent 项目最终回滚到单 Agent | 行业共识 |

### 面试话术

> "多 Agent 不是银弹。我学到的规则是：单 Agent 先跑到能力天花板，确认是任务结构问题而非 prompt 问题，再考虑拆分。拆分时用集中式架构（Manager 仲裁）而不是让 Agent 自由协商。"

## 2. 集中式 vs 去中心化

**标签**: `arch/centralized-vs-decentralized`

| 维度 | 集中式(Manager) | 去中心化(P2P) |
|------|----------------|--------------|
| 错误放大 | 4.4x | 17.2x |
| 通信效率 | Hub-Spoke 线性 | n² 膨胀 |
| 单点故障 | Manager 是瓶颈 | 无单点但难调试 |
| 适用场景 | 任务编排、结果审核 | 探索性讨论 |
| **推荐** | **生产环境首选** | Demo/POC |

### 面试话术

> "Cognition 的结论是 2025 年多 Agent 协作还很脆弱，决策太分散。我选集中式 — Manager 负责任务拆分和结果审核，子 Agent 只做执行不做决策。"

## 3. Context Engineering

**标签**: `arch/context-engineering`

### 核心理念

> Prompt Engineering 教模型"怎么想"，Context Engineering 管模型"看到什么"。后者对可靠性的影响更大。

### 三层存储模型（Google ADK）

```
Session 层（持久真相）
  ↓ 编译
Working Context 层（每次调用临时视图）
  ↓ 缓存
KV Cache 层（推理加速）
```

### 五大操作（Manus 框架）

| 操作 | 含义 | 关联你的代码 |
|------|------|-------------|
| Offloading | 大工具输出存文件系统，context 只留引用 | s06 compaction |
| Reduction | 可逆压缩(compaction) vs 不可逆摘要(summarization) | 三层压缩策略 |
| Retrieval | 文件级检索(grep/glob)用于人尺度，向量库用于企业尺度 | s07 task files |
| Isolation | 功能独立的 Agent 共享沙箱文件系统 | s04 subagent + s12 worktree |
| Caching | KV cache 作为一等设计约束 | — |

### 面试话术

> "Context Engineering 比 Prompt Engineering 更重要。我把上下文当作'编译视图'而不是字符串拼接。每次传给模型的内容是经过确定性组装（排序/归一化）的，大工具输出 offload 到文件系统只留引用。这比调 prompt 对稳定性提升大得多。"

## 4. Harness 设计原则

**标签**: `arch/harness-design`

### Guides（前馈）+ Sensors（反馈）

```
Guides: 在 AI 行动前给正确输入
  ├── 清晰指令
  ├── 相关上下文
  ├── 结构化任务描述
  └── 工具使用边界

Sensors: 在 AI 行动后检验输出
  ├── 独立验证器
  ├── 质量评估
  ├── 异常检测
  └── 熔断机制
```

### 13 种反模式（Atlan 2026）

| 层次 | 占比 | 典型案例 |
|------|------|---------|
| Tier 1 架构层 | ~20% | 巨型 Prompt、隐形状态(LLM作内存)、全有或全无自主权 |
| Tier 2 执行层 | ~25% | 工具膨胀、幻觉参数、Schema 漂移 |
| Tier 3 数据层 | **~55%** | 愚蠢 RAG、上下文漂移(65%故障起因)、静默错误 |

### 面试话术

> "Harness 的核心不是写得多的代码，是写得对的约束。Guides 告诉模型什么能做，Sensors 检验模型做了什么。大部分失败被归因于模型问题，实际是数据层问题 — 88% 的项目卡在这。"

---

## 快速判断清单

面试里被问到架构选择时，按这个顺序回答：

1. **先判断能不能用单 Agent**（准确率够不够、任务拆不拆得开）
2. **必须拆的话，用集中式**（Manager 审核）
3. **不超过 4 个 Agent**
4. **每个 Agent 有独立的 context 和 timeout**
5. **关键步骤有独立验证**（不是自己评估自己）
