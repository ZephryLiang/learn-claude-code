# 01 — 痛点库

> 每个痛点按固定结构记录：现象 → 根因 → 复现条件 → 解决方案

## 1. 上下文退化

**标签**: `pain/context-degradation` `arch/context-engineering`

### 1.1 Lost in the Middle

| 项目 | 内容 |
|------|------|
| **现象** | GPT-4o 在 32K+ token 后准确率从 99.3% → 69.7% |
| **根因** | 模型注意力机制对中间位置信息分配权重低 |
| **复现条件** | 上下文超过 32K token，关键信息在中间位置 |
| **方案** | 关键指令放首尾、上下文压缩(s06)、滑动窗口 |

### 1.2 Reasoning Shift（2026 新发现）

| 项目 | 内容 |
|------|------|
| **现象** | 长上下文下模型推理 token 暴缩 43%（28771 → 16415） |
| **根因** | 模型**主动选择少想**，不是被干扰绕晕。自我验证概率从 43% → 32% |
| **复现条件** | 上下文中有无关内容（128 token 就够触发，推理缩水 18%） |
| **方案** | 上下文裁剪、关键任务注入 calm 情绪向量（Anthropic 研究） |
| **面试价值** | 讲 compaction(s06) 时引入 — "不是省 token，是防模型偷懒" |

### 1.3 上下文碎片化

| 项目 | 内容 |
|------|------|
| **现象** | 多 Agent 间信息传递产生有损压缩，一步错步步错 |
| **根因** | 每个 Agent 拿到的是上个 Agent 的摘要，关键细节丢失 |
| **复现条件** | 3+ Agent 串行传递信息 |
| **方案** | 结构化进度文件(s07)、worktree 共享文件系统(s12) |

## 2. 子 Agent 失控

**标签**: `pain/subagent-runaway` `gap/production-hardening`

### 2.1 互递归死循环

| 项目 | 内容 |
|------|------|
| **真实案例** | GetOnStack 4-agent 系统跑了 **11 天**，$127 → $47,000 |
| **根因** | Agent A 请求 B 帮助，B 反问 A 澄清 → 死锁 |
| **方案** | max_iterations 硬限制 + circuit breaker + 实时 cost 监控 |
| **关联你的项目** | s04 subagent 隔离时加 timeout 参数 |

### 2.2 静默杀手（Silent Killer）

| 项目 | 内容 |
|------|------|
| **现象** | Agent 报告任务完成但实际未执行 |
| **根因** | 接近 context limit 时产生"上下文焦虑"：草草收尾、把未完成标记为完成 |
| **方案** | 独立验证步骤：执行 Agent + 验证 Agent 分离 |
| **关联你的项目** | s09-s10 团队协作中的结果验证协议 |

### 2.3 编排器越权

| 项目 | 内容 |
|------|------|
| **现象** | Orchestrator 自己下场干活，分治策略形同虚设 |
| **根因** | 子 Agent 返回质量差 → 编排器不信任 → 自己重做 |
| **方案** | 子 Agent 输出格式约束 + 部分结果回传(partial result) |

## 3. 多 Agent 协调

**标签**: `pain/multi-agent-coordination` `arch/single-vs-multi`

### 3.1 协调税（Coordination Tax）

| 数据 | 单 Agent | 集中式多 Agent | 混合式多 Agent |
|------|---------|---------------|---------------|
| 平均轮次 | 7.2 | 32.1 | **44.3** (6.2x) |
| 每 1000 Token 成功次数 | 67.7 | 21.5 | **13.6** (1/5) |

**根因**: Token 花在"开会和读指令"上，没时间干活。

### 3.2 错误放大效应

| 架构 | 错误放大倍数 |
|------|------------|
| 独立多 Agent（无纠错） | **17.2x** |
| 集中式（Manager 审核） | 4.4x |

**结论**: 5% 单 Agent 错误率 → 独立多 Agent 可能变成 86%。

### 3.3 停止条件缺失

| 现象 | 说明 |
|------|------|
| Generator-Validator 病态乐观 | Agent 评估自己输出时自我点赞（同一套认知框架） |
| 责任推诿 | 多 Agent 串行时每个环节何时终止没有统一标准 |

**方案**: 独立 Evaluator Agent + 结构化停止条件（轮次上限/质量阈值/cost cap）

## 4. 工具调用可靠性

**标签**: `pain/tool-calling` `interview/tool-calling`

| 痛点 | 现象 | 方案 |
|------|------|------|
| 幻觉参数 | 编造不存在的 API 参数 | 代码层二次校验 + schema 验证 |
| Schema 漂移 | 工具定义变了但 Agent 还在用旧格式 | 版本化工具定义 + 兼容层 |
| 工具膨胀 | 60+ 工具时模型选错概率大增 | 意图分类 → 工具分组 → 按需传 schema |
| MCP 无审计 | 调用完就被"遗忘"，无 trace | immutable event log + 可回放 |

## 5. 生产规模化

**标签**: `pain/production-scale`

| 维度 | POC | 生产 |
|------|-----|------|
| 并发 | ≤10 | 1000+ |
| 准确率 | 稳定 | 高并发下跌 10-30% |
| 成本 | 几百元/月 | 1000 并发下 **单月超百万** |
| 可用性 | ~95% | 需要 99.9%+ |

**真实事故**: 某电商 618 客服 Agent — POC 20 并发 94% 准确率 → 上线 1280 并发准确率 61%，A 用户退款信息返回给 B 用户，直接损失 **400 万**。

## 6. 数据与信任

**标签**: `pain/data-trust`

| 痛点 | 说明 |
|------|------|
| 静默错误 | 输出听起来正确但实际错误，没有任何异常抛出 |
| 上下文漂移 | **65% 企业 Agent 故障起因**是陈旧上下文 |
| 缺少审计 | MCP 调用无日志，出问题无法回溯 |
| 错误归因 | 88% 项目失败被归因于模型问题，实际是数据层问题 |

> **Confluent 的结论**: "It's more of a data problem and a trust problem than a model problem."
